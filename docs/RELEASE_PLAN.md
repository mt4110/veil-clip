# macOS監視CLIの公開準備計画

**2026-10-07：開発・公開準備を凍結しました。以下は保存した実装・検討の記録です。現在の実行予定ではありません。** [凍結理由と再開条件](ARCHIVE_DECISION.md)

[English](RELEASE_PLAN.en.md)

更新日：2026-10-07。今回の承認範囲はM0〜M2の計画整理です。機能実装・実機操作・配布・定期実行の開始は、この計画の作成だけでは承認されません。

最新のM0判断：[付箋・メモからのパスワードコピーの机上評価](PASSWORD_USE_CASE.md)では、現行の検知・通知は用途に合わず不合格です。この用途のM1・M2は停止します。以下は条件付き計画で、進行を約束するものではありません。

## 完成させるもの

macOSでユーザーが手動起動する、機密情報らしいテキストの検知・通知CLIを最初の候補とします。日本語を標準とし、英語でも利用できる状態を目指します。
現在の通知先はターミナルの標準エラーです。OS通知やChatGPTへの通知はありません。本文・抜粋・ハッシュを保存・外部送信しません。上書き・貼り付け阻止・履歴消去・自動起動・GUIは今回の完成条件に含めません。

セキュリティ需要全体から、このツールの需要や収益を推定しません。主力プロダクトの作業を置き換える根拠は未確認です。最初の利用者はmacOSを使う開発者という仮説で、具体的な場面はM0で決めます。全国・世界への展開は最初の利用者が使えると確認した後の判断です。

## M0：対象と価値の確定

状態：未完了。計画は準備済み、利用場面と通知の価値は未確認。

- ユーザーが実際のコピー場面を1つ示す。コピー元・貼り付け先の種類、困りごと、現在の対策だけを使う。
- その場面に適用できる既存手段を確認し、できること・できないこと・未確認を分ける。
- [5作業日の様式](USE_CASE_VALIDATION.md)で普段の作業を確認する。事故を作らず、本文や画面を集めない。
- ターミナルへの通知を見て、必要な対応を取れるか確認する。「消えた」「漏洩を防いだ」と誤解しないことも確認する。

完了条件：対象場面、残る不足、通知を受けて取る行動、通知だけでも使う理由が言葉で示せる。観察記録の件数だけでは合格しない。

終了条件：確認した既存手段で足りる、通知に役割がない、または自動消去・全アプリへの貼り付け阻止が必須なら、この監視CLIの公開計画を停止する。観察機会が不足なら未確認のまま停止し、期間を自動延長しない。CLIの公開を収益化の証明としない。

## M1：監視CLIの品質確認

状態：一部完了。検知・TTL・CLI・ロック単体の既存実装と基本試験は完了。公開用の実機確認は残る。

| 作業 | 確認方法・担当 | 完了条件 |
| --- | --- | --- |
| 読取のみの経路、秘密を出さない出力、依存・ライセンスの確認 | 担当エージェントがコードを確認し、必要なmise検証を実施 | 書込経路がCLIから実行されない。出力と異常系の制約を記録する |
| 日英の検知・期限・取り消し・停止 | ユーザーまたは承認された実機試験。合成ダミーのみ | 実行環境と結果を記録し、クリップボードがツールに変更されないことを確認 |
| スリープ復帰とテキスト以外の入力 | ユーザーが制御した実機手順で確認 | 古い入力を保護済みと誤表示せず、復帰後の読取と停止が確認できる |
| 読取失敗・復帰・出力失敗 | 既存モックを担当エージェントが確認。実機で安全に再現できない失敗は未検証と記録 | 状態遷移を説明でき、失敗を黙って保護成功と扱わない |
| 作業中の負荷と通知の負担 | 合成入力の制御したセッションでCPU・メモリ・通知を確認 | 環境・入力サイズ・期間・測定方法を記録し、使えない負担や継続的な増加がないか判断する |

数値の合格基準は測定前に利用目的に合わせて決め、未測定の性能を約束しません。試験で再現した不具合だけを、原因に絞って修正します。失敗を通すために安全条件を弱めません。

ブロッカー：本文が出る、意図しない書込、通知・停止が実作業で使えない、解消できない資源増加、説明と実装の不一致。既存のOS読取停止中に即時終了を保証できない制約は公開条件として判断し、無期限の調査で隠しません。

## M2：最初の利用者へ届ける準備

状態：未着手。M0の価値とM1の品質が通ってから配布を判断する。

- 日本語READMEを中心に、目的、検知対象、通知の意味、起動・終了・更新・取り除く手順を英語と揃える。
- 初回利用者が自分で合成ダミーを試せる短い手順を用意し、説明どおり実行できるか確認する。
- 最初の配布方式を1つに絞る。ソースからの導入か、macOSバイナリかは導入負担と必要な署名・配布条件を確認して決める。現時点で署名・公証済みと扱わない。
- 配布する版・対応macOS・CPU構成・依存のライセンス・更新方法を明記する。UbuntuのコアCI成功をLinux監視対応としない。
- 非公開のセキュリティ報告窓口を確認・準備し、SECURITYの日英版を揃える。GitHub設定変更は別の具体的承認で行う。
- リリース候補の検証記録・成果物・制約をレビュー可能にする。タグ・リリース・外部配布はユーザーの公開承認を最後の工程にする。

完了条件：最初の利用者が導入・ダミー確認・停止でき、通知のみという限界を理解し、非公開で問題を報告できる。公開前レビューを終える。日本全国の対応や防御効果を保証したとは扱わない。

終了条件：必要な権限・導入負担に対して価値がない、保守や報告対応を継続できない、重大な品質問題が残るなら公開しない。

## 毎日の進め方

1回につき、次の未完了タスクを1つ選び、目的・成果物・確認方法を先に示します。終わりに差分・検証・残る問題・次の1件を記録します。作業量はタスクの小ささで制限し、時間や費用の数字を実測なしで約束しません。

| 順序 | 小さな成果物 | 前提 |
| --- | --- | --- |
| 1（今回） | 日英計画と停止条件、既存記録との対応 | 完了。製品の完成ではない |
| 2 | M0の対象場面と代替手段の比較1件 | ユーザーが場面を提示 |
| 3 | M1の合成ダミー実機手順1件 | M0で通知の価値を判断。実機操作は具体的範囲の承認後 |
| 4以降 | 実機結果1件の整理、または再現した不具合1件の修正 | 必要な品質作業だけを選ぶ |
| M1完了後 | M2の導入・配布準備を1件ずつ | 公開は最終承認後 |

毎日の自動実行はまだ設定していません。手動依頼か定期実行かをユーザーが選びます。定期実行には日本時間の実行時刻と、モデル・作業範囲・終了条件を明示します。入力不足や判断待ちでは実装を進めず、待ち状態を記録します。新しい実機操作・権限変更・公開、範囲拡大やモデル設定変更は自動的に行いません。

## 実現性の早期判定

- 技術：既存の監視CLIは実装済み。一般向けの安全な自動上書きや全経路の貼り付け阻止は、今回の成果として成立していない。
- 価値：ターミナル通知で足りるかはM0で判断。必要なのが防御なら、通知CLIを防御製品と呼ばず停止する。
- 維持：小さな1対象の導入・保守に絞る。複数OS・GUI・監査へ同時に広げない。
- 判断：各段階のブロッカーが分かった時点で、箇所・根拠・影響・代替か中止の提案を示す。完成を約束して判断を先送りしない。
